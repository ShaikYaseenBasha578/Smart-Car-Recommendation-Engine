# Plan: the 22 UI/UX changes, 22 Nov 2026 (awaiting owner approval)

**Source:** a blind review of the live site by a fresh Opus agent, `UIUX_REVIEW_2026-11-22.md` in this folder. The change ids (C1–C22) below are the review's own. Claude checked these claims against `main` before planning, and they hold:
- the data stamp shows the run name (`script.js:244`);
- the "What we understood" chips show only the makes that were asked for;
- the whole results area is `aria-live`;
- "Top pick" is always the first card;
- the chips rotate every 8 s;
- the parser already returns `residual`, the words it did not use.

## Ground rules for every pull request

- **Who does what:** Sonnet subagents write the code in their own worktree and branch from `main`. Opus designs, reviews the diff and checks the screenshots. Owner rules:
  - Use the impeccable skill for all of the UI work.
  - Each PR is opened, never merged by Claude.
  - Screenshots go in every PR: desktop 1280 and mobile 375, light and dark, before and after.
- **No change to what is recommended:**
  - Hard filters, scoring and the parser's constraints stay as they are.
  - Main stays at 193/193 zero-violation and held-out at 105/107. The verified share and recall@8/MRR must not move, and none of the 329 eval parses may change.
  - Only presentation, plus two read-only API additions (PR D), changes.
- **Tests:**
  - The full `tests/` suite passes, including `test_v3_frontend.py` and `ui_gates.py`.
  - New behaviour gets tests: JS-rendered output through the existing frontend tests, and new API fields through the API tests.
- **Branches:** the PRs touch the same files (`static/script.js`, `static/style.css`). So they are built **one at a time**, each from the latest `main` after the previous PR merges. There is no stacking, which is what sent PR 44 to the wrong base. No parallel sessions.

### PR B: the result card, rebuilt (C4, C6, C20)

  - **Targets, measured in the PR:** at most 380 px on desktop and 720 px on mobile.
- **C4, meters:** the three bars are replaced by one line of real values, e.g. "Reviewers: 8/10 (Autocar, above average for SUVs) · Owners: 4.6/5 from 1,068 (above average)".

### PR D: telling the user what was not used (C3b, C3c, C12)
**API, read-only additions:**
- `ignored_terms`: the parser's existing `residual` words, minus a stop list (filler words, numbers already used, Hinglish particles).
- Uncovered brands such as Ferrari go into the existing `unsupported_terms`, from a fixed list of makes sold in India but not in the catalogue.

**UI:**
- "Didn't use: convertible" chips, dashed and quiet.
- The existing notice for an uncovered brand: "We don't cover Ferrari. Showing cars under ₹10 lakh instead."
- **C12:** each relaxation is shown as an undo-able choice ("Seats 7+ → 5+ ✕"), plus "Or drop instead: [Sunroof] [ADAS] [Budget]" buttons using the existing `drop=` URL. The notice is cut to two sentences. Why `relaxation_hints` came back empty for the reviewer's query is found first and fixed in this PR.

**Checks:**
- The "Didn't use" chip must be right, not noisy. Run it over all 329 eval queries and the 40 hard queries, and list every chip shown.
- A fresh blind agent judges a stratified sample of at least 50 (shown vs not shown) without seeing the code; at least 95% agreement in each class (P12 style).
- Parses are unchanged, because the field is display-only.

**Also measured here, not promised:** why vague queries take about 10 s on Render, against 3–4 s for structured ones. It is found and reported, and fixed only if the fix is small and changes no results.

### PR E: compare and sort (C7, C16)
- **C7, compare:**
  - A "Compare" toggle on each card (`aria-pressed`).
  - With 2–4 cars selected, a sticky 64 px tray with "Compare 3 cars".

- **C16, sort:** "Best match / Price / Mileage / Safety" (a native select on mobile), on the shown cars only, and kept in the URL (`&sort=`). "Top pick" and "Closest match" show only in Best match order.
